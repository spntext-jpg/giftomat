# Деплой на платформу VibeCode (build_galaxy)

Опорные технические данные для публикации Giftomat на инфраструктуре VibeCode
(`*.vibecode.bitrix24.tech`). Это рабочий справочник для деплоя этого репозитория,
а не документация платформы целиком.

## 1. Команда публикации

Деплой запускается из вкладки «Код» одним вызовом (или кнопкой «Деплой»), **без
аргументов** — `sessionId` сеанса подставляется автоматически:

```text
vibecode_deploy({})
```

- Рантайм по умолчанию: **node20** (в образе есть node и npm, НЕТ python3/php).
- Другой стек передаётся явно: `vibecode_deploy({ runtime, start, install })`
  (доступны `node20`, `python311`, `php83`, `static`, варианты с СУБД).
- Для Node ничего передавать не нужно — это штатный выбор платформы.

## 2. Что делает сервер при развёртывании

Порядок шагов платформы после публикации:

1. Распаковка архива в `/opt/app`.
2. `npm install`.
3. `npm start`.
4. Ожидание приложения на порту **`process.env.PORT || 3000`**.

⚠️ Рабочая папка на сервере — `/opt/app`, и она переживает передеплой один-в-один.
Данные, которые должны переживать публикацию, пишутся **только в `/data`**
(резолв с фолбэком: `process.env.DATA_DIR || "/data"`, затем папка приложения,
запись атомарно — tmp + rename). Всё рядом с кодом стирается при каждой публикации.

## 3. Модель деплоя Giftomat (static export + node:http)

Giftomat — полностью клиентское приложение, поэтому оно разворачивается как
**статический экспорт**, который отдаёт минимальный сервер — без сборки на хосте:

- `next.config.ts` → `output: "export"` (генерирует `out/`).
- `package.json` → `"start": "node server.js"`.
- `server.js` — только `node:http` (без внешних зависимостей), отдаёт файлы `out/`,
  слушает `process.env.PORT || 3000`, применяет security-заголовки и корректно
  отдаёт `/sw.js`.

Это устраняет главную причину `GALAXY_APP_START_FAILED`: при старте **не**
выполняется тяжёлая `next build` (которая требует devDependencies и времени), сервер
поднимается мгновенно и детерминированно.

## 4. Старт-скрипт и self-healing

```json
"start": "node server.js"
```

`server.js` при старте:

- проверяет наличие `out/index.html`;
- если статика есть — сразу отдаёт её (fast path);
- если `out/` отсутствует — сам запускает `npm run build`, регенерирует `out/` и
  затем отдаёт его (self-healing fallback).

Чтобы статический бандл гарантированно попал в архив деплоя, **`out/` исключён из
`.gitignore`** (иначе упаковщик, уважающий `.gitignore`, его отбрасывает, и сервер
на старте не находит `index.html` → health-check падает).

## 5. Подготовка к публикации (чеклист)

```bash
npm run verify        # typecheck + тесты + smoke + next build
npm run build         # next build c output:"export" → создаёт out/
npm start             # node server.js → локальная проверка на PORT (по умолч. 3000)
```

Проверить, что воркспейс реально разворачивается:

- в корне есть `package.json` с рабочим `start`, поднимающим сервер на
  `process.env.PORT || 3000` (порт не захардкожен — иначе `port_mismatch`);
- `out/` собран и лежит в корне (иначе `GALAXY_APP_START_FAILED` / `app_unhealthy`);
- `npm install && npm start` локально поднимает сервер, отдающий приложение.

## 6. Диагностика ошибок деплоя

| Код | Что значит | Что делать |
|-----|------------|------------|
| `GALAXY_APP_START_FAILED` | приложение не поднялось на порту при старте | причину искать в хвосте `buildLog`; чаще всего — тяжёлая `next build` при старте / нет `out/` |
| `GALAXY_APP_BUILD_FAILED` / `BUILD_FAILED` | упала сборка или `npm install` | смотреть `buildLog`: несуществующий пакет (`404 … not in this registry`), синтаксическая ошибка, `ENOENT /opt/app/package.json` |
| `runtime_mismatch` | стек приложения не совпадает с рантаймом деплоя | передать нужные `runtime`/`start`/`install` (или переписать приложение на Node) |
| `command not found` в `buildLog` | приложению нужен интерпретатор, которого нет в рантайме | то же, что `runtime_mismatch` |
| `port_mismatch` | сервер слушает не тот порт | перевести на `process.env.PORT \|\| 3000` |
| `app_unhealthy` | применилось, но не отвечает на `/` | проверить, что сервер действительно слушает порт и отдаёт 2xx |
| `deploy_key_missing` | у сеанса нет ключа деплоя | взять ключ на https://vibecode.bitrix24.tech/keys (`vibe_api_…`) и добавить |

⚠️ Сборка платформы может не иметь доступа к реестру пакетов: несуществующие
внешние зависимости ловят `ReadTimeoutError`/`ETIMEDOUT`/`ENOTFOUND` на этапе
скачивания. Для такого случая пишем на стандартной библиотеке (у `server.js` —
только `node:http`), а не ретраим деплой с тем же `install`.

## 7. Шлюз и авторизация

Приложение отдаётся по адресу `https://app-<id>.vibecode.bitrix24.tech` за шлюзом
платформы (аутентификация до кода, в стиле Cloudflare Access):

- Свой логин Giftomat не нужен — кто дошёл до приложения, уже вошёл на платформу.
- Шлюз проставляет личность в каждый запрос:
  - `X-Vibe-User-Id` — числовой ID в портале (значения с префиксом `net_`/`share:`/
    `vibe:` означают, что ID в портале нет — в поля REST их подставлять нельзя);
  - `X-Vibe-User-Name-Encoded` — имя (читать через `decodeURIComponent`);
  - `X-Vibe-User-Role` — `ADMIN`/`MEMBER` (надёжная проверка администратора);
  - `X-Vibe-Authorization` — `Bearer vibe_session_…` для серверных вызовов `/v1`.
- Входящие `X-Vibe-*` от клиента шлюз срезает — подделать нельзя.
- Если нужен свой вход: НЕ отдавать куку вместе с редиректом (шлюз сам проходит
  3xx), ставить куку на не-редиректном `200` и переходить на закрытую страницу с
  клиента. Имя куки не должно быть `session` (занято платформой на родительском
  домене `.vibecode.bitrix24.tech`).

Giftomat не использует портальные данные, поэтому шлюзные заголовки здесь не нужны —
но они важны для любой будущей интеграции с данными Битрикс24.

## 8. Данные портала в приложении (если понадобятся)

Доступ к порталу уже настроен через переменные окружения:

- `BITRIX_API_KEY` — ключ портала, заголовок `X-Api-Key`;
- `BITRIX_API_BASE_URL` — базовый адрес REST-прокси (к нему дописывается путь,
  например `/deals`, `/tasks/search`);
- `BITRIX_PORTAL_DOMAIN` — домен портала для ссылок обратно в Битрикс24.

Правила:

- Запросы к порталу делает **только сервер** приложения (фронт ходит на свои
  `/api/*`), ключ не попадает в браузер;
- ключ не хардкодить — читать `process.env`;
- `.env` не читать/не печатать/не коммитить;
- домен для ссылок брать из `BITRIX_PORTAL_DOMAIN`;
- если ключа ещё нет — приложение обязано стартовать: `/api/*` отвечают понятной
  ошибкой, интерфейс показывает «портал не подключён».

## 9. Доступность и «refused to connect» (сон и память Galaxy)

**Симптом.** Сотрудники время от времени получают `refused to connect` при запуске:
браузер не может даже открыть соединение (терминальная ошибка, не страница «нет
доступа»). При этом владельцу открывается, политика доступа `PORTAL` стоит, а сеть
не влияет (не работает и с мобильного интернета).

**Диагноз.** `refused to connect` — это отказ на уровне TCP: в этот момент
приложение просто не слушает порт. Это ошибка **доступности**, а не доступа (отказ
доступа шлюз отдавал бы страницей входа/`4xx`, а не «connection refused», и был бы
одинаков у всех). Причина — в управляемом Galaxy-контейнере, у которого:

- **автосон (scale-to-zero):** `runMode: IDLE`, `sleepAfterMinutes` — сервер
  засыпает после простоя, и тот, кто открывает первым после паузы, попадает в
  холодный старт/пробуждение, когда сервер ещё не слушает;
- **OOM-падение:** поле `provisionReason: "oom"` (контейнеру не хватило памяти) —
  платформа прямо рекомендует при `oom` перенести приложение на выделенный сервер.

Владелец часто открывает приложение и держит его «тёплым», поэтому у него «всё
ок», а отдельные сотрудники попадают в окна, когда контейнер спит или лежит после
краха.

**Лечение (в кабинете VibeCode, на странице сервера):**

1. `runMode` → `ALWAYS` (круглосуточно), чтобы сервер не остывал между открытиями.
2. При `provisionReason: "oom"` / рестартах по памяти — перенести на **выделенный
   (STANDALONE) сервер** с запасом памяти.
3. Убедиться, что `out/` собран и поставляется (см. §4): иначе каждый холодный
   старт гоняет тяжёлый `next build`, который сам жрёт память и минуты.

**Что уже сделано в коде (`server.js`).** Сервер теперь слушает порт **до** любой
сборки и при неготовом бандле отвечает `503` с `Retry-After` и автообновлением
вместо «мёртвого» соединения — браузер перезапросит страницу, а не покажет
`refused to connect`. Это закрывает код-сторонний вклад в симптом; корневую причину
(сон/OOM контейнера) лечит переключение режима/выделенный сервер по пунктам 1–2.

**Важно (не путать с доступом).** Смена политики доступа с `OWNER_ONLY` на
`PORTAL` нужна для того, чтобы сотрудники вообще проходили через шлюз, но сам по
себе `refused to connect` она не лечит — он говорит о лежащем контейнере, а не о
правах.
